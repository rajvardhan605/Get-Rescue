# Get-Rescue Ticket Widget — Working Log

This file is the running record for `app/widget.html` — a Zoho Creator embedded widget that lets an agent create and drive a Get-Rescue (RSR/TOW dispatch) ticket step-by-step. **Read this file first before making changes** — it tracks what's confirmed against the live Zoho account vs. what's still an assumption, has a code map so you don't have to re-read the whole file to know what exists, and a dated log of what's changed.

Update this file whenever a change is made or a schema fact gets confirmed/corrected via live testing. Line numbers below drift as the file changes — if a number looks off, `grep -n` the symbol name rather than assuming the file moved.

---

## 1. What this is

- One HTML/CSS/JS file (`app/widget.html`), embedded as a Zoho Creator widget.
- Zoho Creator is used only as the backend, via the widget SDK's Data API (`getRecords`/`addRecords`/`updateRecordById`) — no `ZOHO.CREATOR.init()` in this SDK build; see `resolve()` for the namespace-scanning pattern used instead.
- **Everything for one ticket lives in a single `Create_Case` record** — added on first save, updated on every subsequent step. `Create_Case.Status` is a real fixed picklist (confirmed 2026-07-28) — every stage writes one of its exact 16 values, never a human-readable stage title.
- A step wizard (`STAGES` array) walks: Create → Quote → Booking Fee → Capture Locations → Vendor Assignment → branch on Service_Type → RSR path *or* TOW path → Final Payment → Final Closure.
- Falls back to demo/sample data (`DEMO`, `DEMO_VEHICLES`, `DEMO_ISSUES`) when the Creator SDK isn't detected, so it's previewable in a plain browser.
- File layout: CSS in `<style>` (~lines 1–195), HTML body/markup (~197–267), all JS in one `<script>` (~268–end).

### Field types (the `t:` value on each field def)
Most are self-explanatory (`text`/`number`/`decimal`/`date`/`tel`/`email`/`textarea`/`select`/`radio`/`check`/`multiselect`/`file`/`badge`/`summary`). Two more, plus two flags that apply to any plain field:
- **`button`** — an action button instead of a checkbox. Saves the same `["Yes"]`/`[]` shape as `check` fields. Two modes: (1) default/one-way (`Send_Payment_Link` on `quote`, `Send_Link_For_The_Breakdown_Location` on `locations`) — click sets the field `true`, button switches to a disabled "done" state (`doneLabel`), no UI way to undo; (2) `repeatable:true` (`Calculate_Distance` on `locations`) — stays clickable forever, for actions you might reasonably redo (e.g. recalculating after fixing a coordinate). Either mode can carry an `action:(record)=>void` hook run on click *before* the re-render — `Calculate_Distance` uses this to set `RT_KM` via `calcRoundTripKm()`.
- **`parseTarget:[fieldA,fieldB]`** (a flag, not a type — put it on a plain `text` field) — on change, splits the field's value on `,` and writes the two parts into `fieldA`/`fieldB`, rounded to 6 decimal places via `roundCoord()` (added 2026-07-28 — see §5). Used by `LatLongPaste` → `Latitude`/`Longitude` and `DropLatLongPaste` → `DropLocationLat`/`DropLocationLong` (see `wireField`'s shared `recompute || parseTarget` branch).
- **`searchable:true`** (a flag on `t:"select"` and `t:"multiselect"` fields) — renders a typeahead combo (`.combo` text input + filtered `.combo-dropdown`) instead of a native `<select>`/`<option>` add-box. Added 2026-07-28 for `Client`, `Vehicle` (both `select`), and `Vehicle_Issue` (`multiselect`'s "+ Add…" box) — these lists can run into the hundreds, where a native dropdown is unusable. Implemented in `wireCombo`/`wireComboAdd` (`buildField`/`wireField`/`wireMultiselect` each branch on it); `collectStep` skips DOM-reading searchable selects entirely (same treatment as `multiselect`/`button`) since the combo's visible input holds a *label*, not the real value — `wireCombo` keeps `state.record[f.n]` current on every pick instead.
- **`row:"someTag"`** (a flag, not a type) — consecutive fields sharing the same `row` string render side-by-side in one full-width `.fld-row` (a 3-column sub-grid, `grid-template-columns:repeat(3,1fr)`, collapsing to 1 column at the phone breakpoint) instead of each taking its own slot in the normal 2-column `.grid`. Added 2026-07-28 for `Customer_Name`/`Phone_Number1`/`Email` on the `create` stage (`row:"contact"`) — the only current user; extend to any 3-across row by tagging consecutive fields the same way (`renderFields` groups them, not the field defs themselves, so order in the `fields` array still matters).
- **`name2` was removed 2026-07-28** — `Customer_Name` used to render as separate First/Last boxes joined into one string on save; now it's a single plain `text` field (see changelog), matching the confirmed real schema (a single-line text field) more directly. All `name2`-specific code in `buildField`/`collectStep`/`buildPayload` was deleted, not just unused.

Everything else — `Vehicle_Issue`, `Vendors`, `Assigned_Technician` — sends plain display text. Don't re-add `useId` to those without new live evidence (see changelog 2026-07-27/28).

## 4. Open questions / unconfirmed assumptions (don't treat as fact — verify before relying on them)

- **6 decimal places for `Latitude`/`Longitude`/`DropLocationLat`/`DropLocationLong` is a best-effort guess, not a confirmed fix.** A live save threw `"Longitude has exceeded its maximum digits"` on a full-precision GPS paste (~15 digits). 6 decimals (standard GPS convention, ~11cm accuracy) is a reasonable guess at fitting under whatever the `Decimal` field's actual configured limit is in Zoho Studio, but that exact limit hasn't been confirmed — if the same error recurs, the field's limit is stricter than 6 decimals and `roundCoord()`'s `1e6` needs to drop (e.g. to `1e4`).
- **What `READY` should actually *mean* is still open — only the "must have a captured location" bug got fixed (2026-07-28).** User said the real intent is "READY comes when assignment and everything is done to vendor and vendor is about to start the work" — i.e. conceptually later in the flow (near/at vendor acceptance), not right after location capture. Given three options (READY on vendor-accepts, READY on assignment-completed, or just fix today's concrete bug), user explicitly chose the narrow fix only: `locations` no longer writes `READY` without a real location, but it still writes `READY` (not some other status) once one exists — the stage READY conceptually belongs to per the user's own description hasn't been decided or moved. Revisit if asked to make `READY` mean "vendor about to start" for real.
- **Locking `Distance_For_Quote_RT_KM` and `Payment_Method` read-only (2026-07-28, explicit request) means neither can currently be populated by the agent at all**, since nothing in the widget sets them automatically. Concretely: no `FORMULA`-rate (TOW) issue can get a real distance-based quote on this step anymore — `calcQuote()` will keep showing "enter distance — distance needed for this issue" forever, since the one way to enter that distance was the now-locked field. Implemented exactly as instructed rather than silently keeping it editable, but flagging clearly since it changes a previously-working calculation path. If a real distance value is meant to arrive from elsewhere (the `locations` step's `RT_KM`, an upstream automation, etc.) before the agent reaches this step, that hookup doesn't exist yet.
- **Root cause of the `CSID...`-style Case_ID sighting is not confirmed.** A real ticket showed a long `CSID`-prefixed Case_ID instead of the widget's own `RSID`+last-6-digits scheme. Best guess: `Case_ID` is a server-side formula/autonumber field that Zoho auto-populates on create, and the widget's follow-up `updateTicket` call to overwrite it with `RSID...` is silently rejected (now caught and `console.warn`'d instead of failing the save — see §3). Not yet confirmed by checking the actual console warning on a fresh save, or by checking the field's type in Zoho Studio. If it turns out `Case_ID` genuinely can't be overwritten via the API, the `RSID` scheme may need to move to a *different*, writable field instead.
- **"There is no OPEN status" was read as confirming already-current behavior, not a new instruction to change `create`'s status.** The user's exact words when specifying the `quote` flow opened with "there will [be] no open status... when they go to next page the ticket['s status] creates with SERVICE FEE QUOTE." Read this as: `OPEN` (the old, never-confirmed guess for the pre-merge `bookingfee` stage) is gone — true since the 2026-07-28 merge — and as a restatement that the *second* step's status is `SERVICE FEE QUOTE`. **Did not** touch the `create` stage's own status, which stays `NEW` (separately user-confirmed earlier the same day). If this reading is wrong and `create` was actually meant to skip straight to some other status, that's a real gap.
- **`cancelWizard()` now saves on every stage, not just `quote`.** The spec only described `quote`'s cancel behavior, but the underlying need (Cancel must persist an accurate `Status` snapshot, not silently discard) isn't stage-specific — generalizing it seemed like the correct, consistent choice rather than special-casing just `quote`. Means Cancel on *any* step now attempts a best-effort save first. Flag if that's too broad a behavior change for stages that weren't part of this request.
- **`Booking_Fee>0` as the zero-fee test** — "if Booking_Fee is zero" was implemented as `!(Number(Booking_Fee)>0)`, which also covers "not entered yet" (empty/`NaN`) and negative values, not just a literal `0`. Reasonable default (no fee typed = nothing to collect yet), but flag if the real intent was strictly `=== 0`.
- **`Total_Service_Fee` vs `Total_Service_Fee1` — likely-duplicate fields, relationship unconfirmed.** Both now sit on the same merged Quote & Booking Fee step, both literally meaning "total service fee." Neither auto-fills the other. Relabeled `Total_Service_Fee1` to "Total Service Fee (Payment Record)" just to reduce agent confusion — don't read that as confirmation they're actually different values; they may need to be kept in sync (or one of them may be legacy/unused) once someone with Studio access can check.
- **`updateRecordById`/`addRecords` via `Agent_Ticket_Report` — untested.** The user only said to *pull* (read) from `Agent_Ticket_Report`; switching updates/adds to it too was my inference (single shared `CONFIG.reportName`, and nothing suggested reads/writes should target different reports). Zoho's `updateRecordById` typically works through any report tied to the same underlying form, so this is *probably* fine, but hasn't been confirmed by an actual save yet — watch for a report-related error on the next save/update and revert just the write path to `Create_Case_Report` if so.

Treat the computed `RT_KM` as an estimate for quoting purposes, not a precise mileage figure; the original architecture notes mention Google Maps distance calculation elsewhere in the app, which this doesn't replicate.
- **The dashboard now shows 4 Status groups, by explicit design (expanded 2026-07-28, see §5)** — New & Open, Ready & Invited, Work In Progress, RSP Closed (exact status lists in §2's `BUCKETS` entry). The only status still left out of all four is **`RSP IRA (INVITE RESPONSE AWAITED)`** (the `assignment` stage's own status) and, notably, the literal **`CLOSED`** status written by the `closure` stage itself — the "RSP Closed" bucket's list is `RSP CANCELLED`/`CX REJECT`/`RSP CLOSED` only, which doesn't include plain `CLOSED`. - **`Vendors` exact save format** — the composite `"[priority] Name | Phone | Status"` string seen on a real record looks Deluge-generated on the native form; the widget doesn't build this yet. Will likely need fixing when the Assignment step is actually tested.
- **`Assigned_Technician` format** — never independently confirmed as text vs. lookup.
- **`Case_ID` truncation-collision risk** — `"RSID"+last 6 digits of record ID` is short by design (user's explicit request) but not mathematically guaranteed unique; two records could theoretically share a 6-digit tail once ticket volume is very high. Acceptable tradeoff as specified, just don't rely on it as a true primary key elsewhere.
- **The real Create_Case form has many fields the widget never touches** — a live record dump showed extra fields like `Selected_Vehicle`, `Selected_Vehicle_Issues`, and multiple `..._Next` fields (e.g. `Create_Service_Ticket_Next`, `Task_Assignment_Next`) that look like section-navigation/helper fields driven by Deluge on the *native* Studio-built form. The widget bypasses the native form entirely and writes directly via the Data API, so these fields are left blank. Unknown whether any downstream automation depends on them being populated.
- **`Rate_Master_Report`'s report link name is a pattern-matched guess** (`CONFIG.rateMasterReport`) — not yet confirmed live, unlike the other `_Report` names which were each confirmed or corrected individually. If the fee calc silently returns "no rate rule found" for everything, check this first.
- **`calcQuote()`'s field-matching assumes plain-text/lookup-display-value equality** — `Rate_Master.Vehicle_Type`/`Vehicle_Segment` are assumed plain picklist text (matching `Vehicle.Category`/`Vehicle.Segment` exactly), and `Rate_Master.Issue` is assumed a Lookup whose display value equals `Vehicle_Issue_Report.Issue_Name` exactly (case-insensitive). Any mismatch (extra whitespace, different casing conventions between the two master tables) will show up as "no rate rule found" even when a rule exists.
- **`Total_Service_Fee` and (as of 2026-07-28) `Rate_Breakup` are only defaulted, not locked to the calculation** — each is set to the computed value only if empty, so an agent's manual edit persists across re-renders. `Suggested_Rate` is still always overwritten by `calcQuote()` on every visit to the Quote step (it's readonly/computed, matching the native Deluge's unconditional `input.Suggested_Rate = totalFee`) — only `Rate_Breakup` changed from "always overwritten" to "seeded once," since it became agent-editable.
- **`Total_Service_Fee` now re-tracks the calculation whenever `Vehicle_Issue` (or `Vehicle`, which clears `Vehicle_Issue`) changes** (2026-07-28) — it's explicitly cleared back to empty at the moment the issue selection changes, so the "seed if empty" logic above recomputes it fresh the next time the Quote step renders, instead of keeping a stale total left over from before the edit. This does mean any manual override of `Total_Service_Fee` is wiped out by a later issue change too — that's the explicit intent ("should be updated as soon as service issues updated"), not an oversight.
- **File uploads are best-effort** — `apiUpload()`'s exact expected signature for `uploadFile` is unconfirmed and never blocks a save if it fails.
- **Status mapping beyond the Create step is a proposal, not confirmed** — only `create → NEW` was explicitly user-confirmed. In particular: (a) `payment → RSP COMPLETE` is a guess — could be `RSP CLOSED` instead; (b) `SCHEDULED` isn't used anywhere yet, though `Time_of_service==="LATER"` at the Create step looks like an obvious candidate; (c) `CX REJECT` isn't modeled — there's no field/button anywhere for "customer rejected the service," so this status can never currently be written; (d) `reachTow` has no Action_field/cancel signal in its field list (unlike RSR's `reach`), so it can't currently set `RSP CANCELLED` even though a cancel is presumably possible there too.
- **Two RSR/TOW stage-ordering bugs fixed 2026-07-28** (inherited from initial build) — `reach` was sequenced *after* `wip` for RSR, and `wipLoadingTow` was sequenced *after* `wipReachedTow` for TOW. Both reordered; worth double-checking the fix reads correctly against the real flow.
- **Resuming a ticket by Status is a best-fit, not exact** — several stages can share the same Status value (e.g. both `acceptance` and `reach` write `RSP ON THE WAY`), so `stageIndexForStatus()` just lands on the *first* matching stage in the path; the agent can still jump to the right step via the stepper.
