# Get-Rescue Ticket Widget — Working Log

This file is the running record for `app/widget.html` — a Zoho Creator embedded widget that lets an agent create and drive a Get-Rescue (RSR/TOW dispatch) ticket step-by-step. **Read this file first before making changes** — it tracks what's confirmed against the live Zoho account vs. what's still an assumption, has a code map so you don't have to re-read the whole file to know what exists, and a dated log of what's changed.

Update this file whenever a change is made or a schema fact gets confirmed/corrected via live testing. Line numbers below drift as the file changes — if a number looks off, `grep -n` the symbol name rather than assuming the file moved.

See also **`QUESTIONS_TO_ASK.md`** (same folder) — a short, current punch list of things that need the client's input or Zoho Studio access to answer, kept separate from this file's much longer §4 so it doesn't get lost in the narrative.

See also **`../FIELDS.md`** (repo root) — the single source of truth for every field API name used across *all* the Get-Rescue widgets (this one plus Technician/Driver/Vendor), organized step-by-step through the ticket's lifecycle. If a field name here ever disagrees with `FIELDS.md`, `FIELDS.md` wins — that's where corrections get made first.

See also **`../ACCESS.md`** (repo root) — which Zoho Creator Forms/Reports this (and every other) widget needs permission to.

---

## 1. What this is

- One HTML/CSS/JS file (`app/widget.html`), embedded as a Zoho Creator widget.
- Zoho Creator is used only as the backend, via the widget SDK's Data API (`getRecords`/`addRecords`/`updateRecordById`) — no `ZOHO.CREATOR.init()` in this SDK build; see `resolve()` for the namespace-scanning pattern used instead.
- **Everything for one ticket lives in a single `Create_Case` record** — added on first save, updated on every subsequent step. `Create_Case.Status` is a real fixed picklist (confirmed 2026-07-28) — every stage writes one of its exact 16 values, never a human-readable stage title.
- A step wizard (`STAGES` array) walks: Create → Quote → Booking Fee → Capture Locations → Vendor Assignment → branch on Service_Type → RSR path *or* TOW path → Final Payment → Final Closure.
- Falls back to demo/sample data (`DEMO`, `DEMO_VEHICLES`, `DEMO_ISSUES`) when the Creator SDK isn't detected, so it's previewable in a plain browser.
- File layout: CSS in `<style>` (~lines 1–195), HTML body/markup (~197–267), all JS in one `<script>` (~268–end).

### Field types (the `t:` value on each field def)
Most are self-explanatory (`text`/`number`/`decimal`/`date`/`tel`/`email`/`textarea`/`select`/`radio`/`check`/`multiselect`/`file`/`badge`/`summary`). Two more, plus two flags that apply to any plain field:
- **`button`** — an action button instead of a checkbox. Saves the same `["Yes"]`/`[]` shape as `check` fields. Two modes: (1) default/one-way (`Send_Payment_Link` on `quote`, `Send_Link_For_The_Breakdown_Location` on `locations`) — click sets the field `true`, button switches to a disabled "done" state (`doneLabel`), no UI way to undo; (2) `repeatable:true` (`Calculate_Distance` on `locations`) — stays clickable forever, for actions you might reasonably redo (e.g. recalculating after fixing a coordinate). Either mode can carry an `action:(record)=>void` hook run on click *before* the re-render — `Calculate_Distance` uses this to set `RT_KM` via `calcRoundTripKm()`.
- **`parseTarget:[fieldA,fieldB]`** (a flag, not a type — put it on a plain `text` field) — on change, splits the field's value on `,` and writes the two parts into `fieldA`/`fieldB`, rounded to 6 decimal places via `roundCoord()` (added 2026-07-28 — see §5). Used by `LatLongPaste` → `Latitude`/`Longitude` and `DropLatLongPaste` → `DropLocationLat`/`DropLocationLong` (see `wireField`'s shared `recompute || parseTarget` branch).
- **`searchable:true`** (a flag on `t:"select"` and `t:"multiselect"` fields) — renders a typeahead combo (`.combo` text input + filtered `.combo-dropdown`) instead of a native `<select>`/`<option>` add-box. Added 2026-07-28 for `Client`, `Vehicle` (both `select`), and `Vehicle_Issue` (`multiselect`'s "+ Add…" box) — these lists can run into the hundreds, where a native dropdown is unusable. Implemented in `wireCombo`/`wireComboAdd` (`buildField`/`wireField`/`wireMultiselect` each branch on it); `collectStep` skips DOM-reading searchable selects entirely (same treatment as `multiselect`/`button`) since the combo's visible input holds a *label*, not the real value — `wireCombo` keeps `state.record[f.n]` current on every pick instead.
- **`row:"someTag"`** (a flag, not a type) — consecutive fields sharing the same `row` string render side-by-side in one full-width `.fld-row` (a 3-column sub-grid, `grid-template-columns:repeat(3,1fr)`, collapsing to 1 column at the phone breakpoint) instead of each taking its own slot in the normal 2-column `.grid`. Added 2026-07-28 for `Customer_Name`/`Phone_Number1`/`Email` on the `create` stage (`row:"contact"`) — the only current user; extend to any 3-across row by tagging consecutive fields the same way (`renderFields` groups them, not the field defs themselves, so order in the `fields` array still matters).
- **`name2` was removed 2026-07-28** — `Customer_Name` used to render as separate First/Last boxes joined into one string on save; now it's a single plain `text` field (see changelog), matching the confirmed real schema (a single-line text field) more directly. All `name2`-specific code in `buildField`/`collectStep`/`buildPayload` was deleted, not just unused.
- **`readonly:true` now works on every field type, not just text-like inputs/textareas/file** (generalized 2026-07-31 for the vendor-stage `viewOnly` lock, see §5) — `select` maps it to the existing `disabled` attribute (same as `f.disabled`; `<select>` has no true `readonly`), `check` disables the checkbox, and `radio` both styles its `.opt` divs as locked (`.radio-set.locked` CSS) **and** has `wireField()` skip attaching their click handlers entirely — the divs aren't real form controls, so `disabled`/`readonly` attributes alone wouldn't have stopped clicks. Not generalized: `multiselect`/`button` (no field of either type currently needs it).

### Fields flagged `useId:true` (send record ID, not display text — see §3 confirmed facts)
**`Vehicle`** (create stage, Lookup to `vehicle_master_Report`) and **`Client`** (create stage, Lookup to `Client_Report`). Everything else — `Vehicle_Issue`, `Vendors`, `Assigned_Technician` — sends plain display text. Don't re-add `useId` to those without new live evidence (see changelog 2026-07-27/28).

## 4. Open questions / unconfirmed assumptions (don't treat as fact — verify before relying on them)

- **`Remaining_Fee` appears in two Final Closure summary groups** ("Service Fee & Booking" from the `quote` stage's own `readonly:true` copy, and "Final Payment" from the `payment` stage's editable copy — confirmed via an isolated `closureFieldGroups()` run, 2026-07-31) since `closureFieldGroups()` intentionally pulls straight from `STAGES` rather than deduping. Harmless in practice (the field is genuinely editable via the real wizard's `payment` step already), just don't be surprised the "Service Fee & Booking" row's popup lets you type into what looks like it should be read-only there.

- **The lat/long precision cap was raised from 6 to 17 decimal places per explicit request (2026-07-30)** — but a live save then confirmed "…exceeded its maximum digits" still fires at 17. Rather than guess a fixed lower cap, saves now auto-retry at progressively fewer decimal places on that exact error (`saveWithCoordFallback()`, see §5) until Zoho accepts one. The `Decimal` field's real configured digit limit in Zoho Studio is still not confirmed — the retry mechanism works around not knowing it, but doesn't tell you what it actually is. If tickets keep saving with visibly rounded-down coordinates (check the console for the retry warnings), that's the signal to go check the field's actual Studio configuration directly.

- **Status mapping beyond the Create step is a proposal, not confirmed** — only `create → NEW` was explicitly user-confirmed. - **`vendors_Report`'s field names for phone/priority/online-offline-status/latitude/longitude are pattern-matched guesses, not confirmed live** (added 2026-07-30, see `CONFIG.vendorFieldCandidates` and §5). Also unconfirmed: whether `vendors_Report` even exposes each vendor's own location at all (vs. only ever the *ticket's* breakdown location) — if it doesn't, the 8km radius filter can never find a match and will always fall back to showing every vendor.
- **The 8km radius (`CONFIG.vendorDistanceKm`) is a straight-line Haversine distance, same caveat as `calcRoundTripKm`** — real road distance to a vendor will usually be larger than this, so a vendor just outside 8km by road might still pass the straight-line filter, and vice versa. Treat it as a rough proximity filter, not a guarantee.

### 2026-08-03 — Real bug fixed: Tab key jumping back to the first field; dashboard "Paid" flag tightened; Final Closure made collapsible

**Root cause found for the reported "pressing Tab jumps back to the top of the form" bug**: several field types (`recompute`/`parseTarget` fields like `Total_Service_Fee`/`LatLongPaste`, the `button` branch, plain `select`/radio/searchable-combo changes) fire a full `renderWizard()`/`renderClosure()` rebuild from their own native `change` handler. The browser's `change` event for a text-like input fires on blur — which, for a Tab keypress, happens *after* the browser has already moved focus to the next field. Destroying and rebuilding the whole fields DOM at that exact moment also destroys the element focus had just landed on, silently dropping focus to nothing — so the *next* Tab press has nothing to advance from and restarts at the very first focusable element on the page. Fixed with a new `preservingFocus()` wrapper (used by `rerenderCurrentView()`, which every one of these handlers now routes through instead of calling `renderWizard()` directly): it remembers the just-focused element's id before the rebuild and refocuses the equivalent freshly-built element right after, so Tab continues normally on the next press.

This was on top of the earlier (2026-07-31) roving-tabindex fix for the custom Yes/No-style radio pickers themselves (which had no `tabindex` at all before that, so Tab silently skipped over them) — both together should make Tab behave like a normal form now.

**Final Closure sections are now collapsible**, same chevron-toggle pattern the dashboard's report buckets already use (`closureGroupHtml`) — click a group's header (Customer & Vehicle, Service Fee & Booking, etc.) to collapse/expand it; state persists across re-renders.
